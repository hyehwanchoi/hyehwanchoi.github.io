> 레거시 표절검사 서비스 MSA 전환기 시리즈의 두 번째 글입니다.  
> 전환 배경과 서비스 경계를 나눈 과정은 [1편: 모놀리식에서 이벤트 기반 구조로](/study/MSA/)에서 다뤘습니다.

1편에서는 PHP 기반 레거시 서비스의 일부를 Java와 Spring Boot 기반 모듈로 분리한 배경을 정리했다. 이번 글에서는 그 과정에서 Kafka를 이용해 처리 단계를 분리한 방법과, 전환 이후 안정화 과정에서 배운 내용을 기록하려고 한다.

Kafka를 도입했다고 해서 곧바로 이벤트 기반 아키텍처가 완성되는 것은 아니었다. 메시지를 어디에서 발행할지, 실패한 처리를 어떻게 확인할지, 기존 시스템과 새 모듈의 책임을 어디까지 나눌지를 계속 조정해야 했다.

---

## 1. 동기 처리 구조에서 시작된 문제

표절검사 서비스에는 문서 접수부터 전처리, 검사, 결과 생성까지 여러 처리 단계가 있었다. 레거시 구조에서는 이 과정의 책임이 한 프로세스에 집중되어 있었고, 앞 단계와 뒤 단계가 강하게 연결되어 있었다.

대량 문서가 유입되면 특정 처리 단계의 지연이 전체 흐름에 영향을 줬다. 일부 기능만 확장하거나 배포하기도 어려웠다. 한 단계에서 오류가 발생했을 때 어느 지점까지 처리되었는지 확인하는 일도 쉽지 않았다.

우리가 해결하려던 문제는 단순히 처리 속도를 높이는 것만이 아니었다.

- 처리 단계를 독립적으로 배포하고 확장할 수 있어야 했다.
- 뒤쪽 시스템의 지연이 앞쪽 요청에 바로 전파되지 않아야 했다.
- 각 단계의 성공과 실패를 구분해 확인할 수 있어야 했다.
- 기존 서비스를 한 번에 교체하지 않고 점진적으로 전환해야 했다.

이 요구를 만족하기 위해 레거시 프로세스를 분석하고, 분리 가능한 구간부터 메시지 기반으로 연결했다.

## 2. Kafka는 경계를 연결하는 수단이었다

새로운 모듈은 Java와 Spring Boot로 구성하고, 처리 단계 사이에는 Kafka를 사용했다. 기존 시스템이 다음 모듈을 직접 호출하는 대신 필요한 정보를 메시지로 발행하고, Consumer가 이를 받아 자신의 작업을 수행하도록 했다.

```text
레거시 서비스
  -> 대상 데이터 조회
  -> Kafka 메시지 발행
  -> 전처리 모듈
  -> 표절검사 모듈
  -> 후속 처리
```

내가 담당한 일은 기존 소스를 분석해 메시지를 발행할 수 있는 구간을 찾고, 대상 데이터를 조회한 뒤 후속 처리에 필요한 메시지를 발행하는 기능을 구현하는 것이었다. 모듈 사이의 연동을 검증하고, 전환 과정에서 발견된 누락과 오류를 개선하는 작업도 함께 진행했다.

여기서 중요했던 것은 Kafka 자체보다 메시지 앞뒤의 책임을 정하는 일이었다. Producer가 어디까지 처리하고 Consumer가 무엇을 책임지는지가 불분명하면, 시스템을 분리해도 문제의 위치만 달라질 뿐이었다.

## 3. 메시지 경계를 정할 때 확인한 것

레거시 코드를 읽으며 먼저 하나의 요청이 어떤 데이터와 기능을 거치는지 추적했다. 화면 요청, 비즈니스 로직, 데이터베이스 변경, 외부 호출이 한 흐름에 섞여 있었기 때문에 코드의 메서드 단위가 곧 서비스 경계가 되지는 않았다.

분리 여부를 판단할 때는 다음 질문을 확인했다.

1. 이 단계는 앞 단계의 트랜잭션과 반드시 함께 완료되어야 하는가?
2. 사용자가 결과를 즉시 받아야 하는가?
3. 같은 메시지가 다시 들어와도 안전하게 처리할 수 있는가?
4. 실패했을 때 재처리할 기준과 상태가 있는가?
5. 이 기능만 독립적으로 배포하거나 확장할 가치가 있는가?

비동기로 넘길 수 있고 독립 확장의 효과가 큰 구간은 Kafka로 분리했다. 반대로 즉시 응답이나 강한 데이터 정합성이 필요한 구간은 기존 동기 흐름을 유지했다. 일부는 스케줄러가 처리 대상을 조회해 메시지를 발행하는 방식으로 점진적으로 연결했다.

결과적으로 모든 기능을 이벤트로 만드는 것보다, 운영할 수 있는 경계를 선택하는 것이 더 중요했다.

## 4. 메시지 발행 이후가 더 중요했다

처음에는 Producer가 메시지를 정상적으로 발행하면 역할이 끝난다고 생각하기 쉬웠다. 하지만 운영에서는 발행 성공만으로 전체 업무의 성공을 보장할 수 없었다.

Consumer 처리 실패, 특정 단계의 지연, 데이터 누락, 중복 처리 가능성을 함께 봐야 했다. 서비스가 분리된 뒤에는 하나의 로그 파일만으로 전체 흐름을 확인하기 어려웠기 때문에 Kafka의 메시지 흐름과 애플리케이션 로그, Zipkin trace를 함께 확인했다.

특히 다음 항목이 중요했다.

- 메시지가 의도한 시점에 발행되었는지
- Consumer가 메시지를 가져간 뒤 정상 완료했는지
- 특정 처리 단계에 지연이 누적되는지
- 실패한 데이터를 식별하고 다시 처리할 수 있는지
- 서비스 사이의 요청 흐름이 trace로 연결되는지

MSA 전환은 배포 단위를 나누는 것으로 끝나지 않았다. 나뉜 프로세스의 상태를 관찰하고 장애 지점을 좁힐 수 있어야 비로소 운영 가능한 구조가 되었다.

## 5. 전환 후 연착륙 과정

MSA 전환 직후에는 기존에 보이지 않던 버그와 예외 상황이 드러났다. 앞 단계는 성공했지만 뒤 단계가 실패하는 경우, 처리 순서가 예상과 다른 경우, 일부 데이터만 누락되는 경우처럼 분산 환경에서 새롭게 확인해야 할 문제가 있었다.

전환 후 안정화 프로젝트에서는 이러한 문제를 프로세스 단위로 나눠 확인했다.

1. 입력 데이터와 발행 메시지를 비교했다.
2. Consumer별 처리 로그와 trace를 연결했다.
3. 실패 조건을 재현하고 누락된 예외 처리를 보완했다.
4. 모듈 사이의 책임이 겹치거나 비어 있는 구간을 조정했다.
5. 수정 후 전체 흐름과 개별 모듈을 함께 검증했다.

이 과정을 통해 전환 과정에서 발생한 버그와 오류의 대부분을 개선했고, 내부 집계 기준 약 99%를 해결하며 서비스 안정화에 기여했다. 중요한 것은 오류 건수를 줄인 결과뿐 아니라, 문제가 생겼을 때 어느 처리 단계부터 확인해야 하는지 팀이 공통된 기준을 갖게 된 점이었다.

## 6. 독립 배포와 확장의 의미

모듈을 분리하면서 특정 기능을 다른 서비스와 독립적으로 배포하고 확장할 수 있는 기반이 생겼다. 대량 문서가 유입되어 특정 단계의 처리량이 증가해도 해당 모듈을 중심으로 대응할 수 있게 되었다.

하지만 서비스 수가 늘어난 만큼 운영 복잡도도 커졌다. Kafka, 데이터베이스, 배포 파이프라인, 로그와 trace를 함께 이해해야 했고, 한 모듈만 정상이라고 해서 전체 프로세스가 정상인 것도 아니었다.

그래서 독립성은 단순히 프로젝트를 여러 개로 나누는 데서 생기지 않는다고 느꼈다. 다음 조건이 함께 갖춰져야 했다.

- 모듈의 책임과 데이터 소유권이 명확할 것
- 메시지 계약을 변경할 때 영향 범위를 알 수 있을 것
- 실패와 재처리 방법이 정의되어 있을 것
- 모듈별 배포와 전체 흐름 검증이 가능할 것
- 로그와 trace로 처리 과정을 추적할 수 있을 것

## 7. 이후 프로젝트에 적용한 기준

이 경험은 이후 신규 서비스와 메시징 전환 프로젝트의 기준이 되었다.

신규 서비스인 GPTKiller를 설계할 때는 처음부터 멀티 모듈 구조로 프로젝트를 구성했다. 출처검사 서비스에서는 Spring Boot, Kafka, SQS와 배포 자동화 환경을 활용해 신규 프로세스와 레거시 연동을 함께 설계했다. CKPASS에서는 기존 프로세스가 다른 서비스의 배포와 처리 속도에 영향을 주는 문제를 줄이기 위해 SQS 기반 메시징으로 전환했다.

모든 프로젝트에 같은 기술을 적용한 것은 아니다. Kafka가 적합한 흐름도 있었고 SQS가 더 단순한 선택인 경우도 있었다. 공통적으로 적용한 원칙은 처리 단계를 분리하기 전에 책임, 실패, 재처리, 운영 방법을 먼저 확인하는 것이었다.

## 8. 다시 설계한다면

지금 같은 전환을 다시 진행한다면 구현 전에 다음 항목을 더 명확하게 정의할 것이다.

- 이벤트 이름과 payload schema, 버전 관리 기준
- 메시지 중복을 고려한 멱등성 처리
- 재시도 횟수와 실패 메시지 보관 방식
- Consumer lag과 처리 시간에 대한 경보 기준
- 배포 전후 메시지 호환성 검증
- 서비스 전체 흐름을 확인하는 통합 테스트

당시에는 전환과 안정화를 진행하며 이런 기준을 하나씩 배웠다. 지금은 메시지 브로커를 붙이는 것보다, 메시지가 실패하거나 늦거나 중복되어도 서비스를 운영할 수 있는지를 먼저 생각한다.

## 마무리

Kafka를 활용한 MSA 전환에서 가장 어려운 일은 메시지를 보내고 받는 코드를 만드는 것이 아니었다. 레거시 프로세스의 실제 책임을 이해하고, 비동기로 분리해도 되는 경계를 찾고, 전환 이후 발생한 문제를 운영 가능한 방식으로 정리하는 일이었다.

이 경험을 통해 MSA는 시스템을 작게 나누는 기술이 아니라 변경과 장애의 범위를 관리하는 설계라는 점을 배웠다. 그리고 전환의 완성도는 최초 설계보다 안정화 과정에서 더 선명하게 드러난다는 것도 알게 되었다.
