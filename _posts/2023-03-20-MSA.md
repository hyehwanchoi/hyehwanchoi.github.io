> 레거시 표절검사 서비스 MSA 전환기 시리즈의 첫 번째 글입니다.  
> 1편에서는 전환 배경과 서비스 경계를 나눈 기준을, [2편에서는 Kafka로 프로세스를 분리하고 안정화한 경험](/study/MSA-2/)을 다룹니다.

이번 글은 회사에서 경험했던 MSA 전환 프로젝트를 정리한 글이다.  
당시에는 PHP 기반의 레거시 모놀리식 서비스 일부를 Java/Spring Boot 기반의 독립 실행 가능한 모듈로 분리하고, Kafka를 이용해 다음 처리 단계로 메시지를 넘기는 구조를 만들었다.

지금 다시 돌아보면 단순히 "MSA를 적용했다"는 경험보다, **어떤 기능을 분리할 수 있고 어떤 기능은 당장 분리하면 위험한지 판단했던 과정**이 더 중요했다.  
레거시 시스템을 새로운 구조로 바꾸는 일은 기술 선택보다 기존 프로세스 이해, 장애 영향 범위 파악, 전환 순서 결정이 훨씬 더 어려웠다.

---

## 1. 왜 MSA 전환이 필요했나

당시 메인 서비스는 PHP 기반의 모놀리식 구조로 운영되고 있었다.  
서비스가 오래 운영되면서 기능이 계속 누적되었고, 하나의 프로세스 안에서 여러 업무 흐름이 강하게 얽혀 있었다.

문제는 다음과 같았다.

1. 하나의 기능 장애가 다른 기능의 처리 지연으로 이어질 수 있었다.
2. 특정 처리량이 증가하면 전체 서비스의 배포와 확장에 영향을 줬다.
3. 기능별 책임 경계가 명확하지 않아 장애 위치를 빠르게 좁히기 어려웠다.
4. 일부 기능만 수정하더라도 전체 레거시 흐름을 함께 고려해야 했다.

특히 표절검사처럼 대량 문서가 유입되는 서비스는 처리량이 특정 시간대에 몰릴 수 있다.  
그래서 모든 처리를 하나의 흐름에서 끝내기보다, 기능 단위로 분리하고 메시지 기반으로 다음 단계에 넘기는 구조가 필요했다.

## 2. 전환 방향

전환의 핵심은 레거시 기능을 한 번에 모두 갈아엎는 것이 아니었다.  
먼저 기존 프로세스를 분석하고, 독립적으로 분리해도 서비스 흐름이 깨지지 않는 영역을 찾았다.

당시 사용한 주요 기술은 다음과 같다.

- Java
- Spring Boot
- Kafka
- JPA
- MariaDB
- Zipkin
- Sleuth
- PHP

Kafka는 서비스 간 메시지를 전달하는 용도로 사용했고, Zipkin과 Sleuth는 분리된 서비스 사이의 흐름을 추적하기 위해 사용했다.  
MSA로 나누면 서비스 수가 늘어나기 때문에, 어디서 지연이 발생하는지 확인할 수 있는 추적 체계가 꼭 필요했다.

## 3. 내가 담당했던 부분

내가 맡았던 부분은 레거시 화면 또는 API 흐름에서 대상 데이터를 조회하고, 이후 처리 프로세스로 넘기기 위한 메시지를 발행하는 기능이었다.

구체적으로는 다음과 같은 일을 했다.

1. 기존 레거시 프로세스 분석
2. MSA로 분리 가능한 처리 구간 식별
3. 메시지 발행 대상과 payload 구조 확인
4. Kafka 기반 이벤트 발행 기능 구현
5. 다음 처리 단계와의 연동 흐름 검증
6. 전환 이후 발생한 오류와 누락 케이스 개선

작은 범위의 기능처럼 보였지만 실제로는 간단하지 않았다.  
레거시 코드에는 화면, 비즈니스 로직, DB 접근, 다음 프로세스 호출이 한 흐름 안에 섞여 있었다. 그래서 먼저 "이 기능이 실제로 어디까지 책임지는가"를 파악해야 했다.

그 다음에는 기능을 무리하게 쪼개기보다, 메시지로 넘겨도 되는 지점과 여전히 동기적으로 처리해야 하는 지점을 구분했다.

## 4. 모든 것을 이벤트 기반으로 만들 수는 없었다

처음에는 MSA라고 하면 모든 기능을 이벤트 기반으로 느슨하게 연결하면 된다고 생각했다.  
하지만 실제 전환 과정에서는 그렇게 단순하지 않았다.

일부 기능은 이벤트 기반으로 전환하기 어려웠다.

- 사용자가 즉시 결과를 확인해야 하는 기능
- 기존 레거시 트랜잭션과 강하게 묶인 기능
- 실패 시 보상 처리 기준이 명확하지 않은 기능
- 데이터 정합성을 먼저 보장해야 하는 기능

그래서 일부는 Kafka 메시지 기반으로 전환했고, 일부는 스케줄러를 통해 메시지를 발행하는 방식으로 처리했다.  
완전한 이벤트 기반 구조는 아니었지만, 당시 시스템의 리스크를 고려하면 점진적인 전환이 더 현실적인 선택이었다.

이 경험을 통해 MSA 전환은 기술을 적용하는 일이 아니라, **전환 가능한 경계와 운영 가능한 수준을 함께 결정하는 일**이라는 것을 배웠다.

## 5. MSA 전환 후 마주한 문제

서비스를 분리하면 장애 영향 범위가 줄어들 것이라고 생각했다.  
하지만 실제 운영에서는 한 서비스의 장애가 뒤쪽 처리 지연으로 이어지고, 메시지가 쌓이면서 전체 흐름에 영향을 주는 경우가 있었다.

MSA에서는 장애가 사라지는 것이 아니라 장애의 모양이 달라진다.

모놀리식에서는 하나의 애플리케이션 안에서 문제가 보였다면, MSA에서는 다음과 같은 지점을 함께 봐야 했다.

- 메시지가 정상적으로 발행되었는가
- Consumer가 정상적으로 처리하고 있는가
- 특정 단계에서 지연이 누적되고 있지 않은가
- 실패한 메시지를 재처리할 수 있는가
- 서비스 간 trace가 이어지고 있는가

이때 Kafka lag, 애플리케이션 로그, Zipkin trace를 함께 확인하는 방식이 중요했다.  
서비스를 나누는 것만으로는 충분하지 않고, 나뉜 서비스를 관찰할 수 있는 운영 체계가 함께 필요했다.

## 6. 장점과 단점

### 장점

1. 기능별 책임이 분리되어 변경 범위를 좁힐 수 있었다.
2. 특정 기능을 독립적으로 배포하고 확장할 수 있는 기반이 생겼다.
3. 장애가 발생한 처리 단계를 이전보다 더 명확하게 추적할 수 있었다.
4. 공통으로 재사용 가능한 처리 흐름을 별도 서비스로 분리할 수 있었다.

### 단점

1. 서비스 수가 늘어나면서 운영 포인트가 증가했다.
2. Kafka, trace, 배포 파이프라인 등 함께 관리해야 할 기술 요소가 많아졌다.
3. 서비스 간 계약이 명확하지 않으면 오히려 장애 분석이 어려워졌다.
4. 담당자가 특정 서비스의 앞뒤 흐름을 모르면 문제 해결이 늦어질 수 있었다.

MSA의 장점은 구조만 바꾼다고 바로 생기지 않는다.  
서비스 경계, 메시지 계약, 실패 처리, 모니터링, 배포 체계가 함께 준비되어야 장점이 드러난다.

## 7. 이 경험으로 배운 것

이 프로젝트를 통해 가장 크게 배운 것은 레거시 전환에는 순서가 있다는 점이다.

내가 생각하는 순서는 다음과 같다.

1. 기존 프로세스를 먼저 정확히 이해한다.
2. 장애 영향 범위와 병목 구간을 찾는다.
3. 분리 가능한 기능과 당장 분리하면 위험한 기능을 구분한다.
4. 작은 단위부터 메시지 기반으로 전환한다.
5. 로그, trace, 메시지 상태를 함께 볼 수 있게 만든다.
6. 전환 이후 발생하는 오류를 안정화하며 경계를 조정한다.

당시 프로젝트 이후 메인 기능을 MSA로 전환하는 작업과 안정화 작업도 이어서 경험했다.  
전환 과정에서 발생한 버그와 오류를 줄이고, 각 프로세스가 독립적으로 동작할 수 있도록 개선하면서 MSA는 설계보다 운영에서 더 많이 배운다는 생각을 하게 되었다.

## 8. 앞으로 더 보완하고 싶은 부분

지금 다시 같은 일을 한다면 다음 부분을 더 신경 쓸 것 같다.

- 이벤트 payload schema를 더 명확하게 정의하기
- 실패 메시지 재처리 전략을 먼저 설계하기
- Kafka lag과 처리 시간을 기준으로 alert 구성하기
- 서비스 간 trace를 운영 기준으로 정리하기
- 어떤 기능을 MSA로 분리하지 않을지도 명확히 결정하기

MSA는 정답이라기보다 선택지 중 하나라고 생각한다.  
중요한 것은 서비스를 작게 나누는 것이 아니라, **변경과 장애를 감당할 수 있는 구조로 만드는 것**이다.

이 경험은 이후 새로운 서비스를 설계하거나 레거시 시스템을 개선할 때 큰 기준이 되었다.  
기능을 만들기 전에 먼저 경계를 보고, 메시지 흐름과 운영 가능성을 함께 생각하게 되었기 때문이다.
