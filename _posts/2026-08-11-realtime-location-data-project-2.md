[지난 글](/project/realtime-location-data-project/)에서는 주기적으로 처리하던 데이터 흐름을 이벤트 중심 구조로 바꾸고, 처리량과 지연을 확인한 과정을 정리했습니다.

구조를 변경한 뒤 Kafka 전송 지연과 연결 오류가 반복됐습니다. 처음에는 애플리케이션의 처리 속도나 Producer 설정을 의심했습니다. 그러나 서버와 토픽 상태를 함께 확인해보니 실제 원인은 다른 곳에 있었습니다.

이 글에서는 잘못 판단했던 원인을 어떻게 다시 확인했는지, 운영 반영 전에 무엇을 검증해야 하는지 정리합니다. 트래픽 증가로 함께 드러난 디스크 사용량과 외부 시스템 연동 성능 문제도 다룹니다. 실제 서버명, 토픽명, 보관기간과 처리 기준은 일반화했습니다.

---

## 1. 처음에는 애플리케이션 성능 문제라고 생각했습니다

메시지 전송이 지연되거나 연결이 끊겼다는 로그를 보면 먼저 Producer와 Consumer 설정을 살펴보기 쉽습니다. 저도 배치 크기, 전송 대기시간, Consumer 처리 지연과 같은 항목부터 확인했습니다.

하지만 애플리케이션 설정만으로는 다음 현상을 설명하기 어려웠습니다.

- 같은 이름의 토픽이 서버에 따라 다르게 보였습니다.
- 일부 서버를 통해 조회한 토픽의 파티션과 상태가 일치하지 않았습니다.
- 특정 서버의 Kafka 상태가 불안정할 때 전송 실패가 반복됐습니다.
- 애플리케이션을 재시작하거나 설정을 조정해도 증상이 다시 발생했습니다.

문제를 애플리케이션 내부에서만 찾고 있었기 때문에 실제 원인을 늦게 확인했습니다.

## 2. 실제 원인은 자동 토픽 생성과 클러스터 구성에 있었습니다

당시 브로커에는 자동 토픽 생성이 활성화되어 있었습니다. 클라이언트가 존재하지 않는 토픽에 접근하면 브로커의 기본 설정에 따라 토픽이 만들어질 수 있는 상태였습니다.

여러 서버를 하나의 클러스터로 구성했다고 생각했지만, 토픽과 브로커 상태를 비교해보니 클러스터 메타데이터가 기대한 방식으로 공유되지 않고 있었습니다. 그 결과 클라이언트가 접속한 서버에 따라 같은 이름의 토픽이 서로 다른 환경에 자동 생성되는 현상이 나타났습니다.

정상적인 하나의 Kafka 클러스터라면 토픽 메타데이터는 클러스터 전체에서 공유됩니다. 서버마다 같은 이름의 토픽이 독립적으로 만들어진 것처럼 보인다면 단순한 토픽 문제가 아니라 다음 항목을 함께 확인해야 합니다.

- 클라이언트가 정말 같은 클러스터의 브로커에 접속하고 있는가
- 각 브로커가 동일한 메타데이터 관리 영역에 참여하고 있는가
- 브로커 식별자가 중복되지 않았는가
- 브로커가 외부에 알리는 주소가 실제 접속 가능한 주소인가
- 컨트롤러와 브로커 상태가 정상인가
- 토픽의 leader와 replica가 정상적으로 할당되었는가
- ISR에서 이탈한 replica가 없는가

여기에 토픽이 생성된 서버의 Kafka가 정상적으로 동작하지 않으면서 leader 조회와 메시지 전송이 실패했습니다. 당시 확인했던 전송 지연과 연결 오류는 애플리케이션 버퍼가 느려서 발생한 문제가 아니라, 클라이언트가 정상적으로 사용할 수 없는 토픽과 브로커 상태를 만난 결과였습니다.

자동 토픽 생성 하나만이 장애의 원인은 아니었습니다. 클러스터 구성이 정상적이지 않은 상태에서 자동 생성이 켜져 있었기 때문에 잘못된 구성이 더 늦게 발견됐고, 의도하지 않은 형태의 토픽이 만들어질 수 있었습니다.

## 3. 운영에서는 토픽을 명시적으로 생성해야 합니다

개발 환경에서는 자동 토픽 생성이 편리할 수 있습니다. 그러나 운영에서는 토픽 생성 자체를 배포 절차의 일부로 관리하는 편이 안전합니다.

운영 반영 시에는 다음 순서로 확인하도록 정리했습니다.

### 클러스터 구성을 먼저 확인합니다

- 브로커별 식별자가 고유한지 확인합니다.
- 모든 브로커가 같은 클러스터와 컨트롤러 구성을 바라보는지 확인합니다.
- 내부 주소와 외부에 알리는 주소가 실제 네트워크 구성과 일치하는지 확인합니다.
- 브로커 프로세스가 실행 중이라는 사실뿐 아니라 클러스터에 정상 참여했는지 확인합니다.
- 브로커 한 대를 중단했을 때도 leader가 정상적으로 전환되는지 확인합니다.

### 자동 생성 대신 토픽을 미리 생성합니다

운영 브로커에서는 가능한 한 `auto.create.topics.enable=false`를 사용하고, 애플리케이션 배포 전에 필요한 토픽을 명시적으로 생성합니다.

토픽 생성 정보는 명령어를 한 번 실행하고 끝내는 것이 아니라 배포 산출물로 관리해야 합니다.

- 토픽 이름
- 파티션 수
- replication factor
- `min.insync.replicas`
- 보관 정책
- 압축 또는 삭제 정책
- 메시지 크기 제한

토픽 생성 스크립트나 배포 자동화에 이 설정을 포함하면 환경마다 기본값이 달라지는 문제를 줄일 수 있습니다.

### 애플리케이션 투입 전에 상태를 검증합니다

토픽을 생성한 뒤에는 다음 항목을 확인합니다.

- 모든 파티션에 leader가 존재하는가
- replica가 의도한 브로커에 분산되어 있는가
- ISR 개수가 기대한 값과 일치하는가
- 테스트 메시지를 발행하고 다시 소비할 수 있는가
- 서로 다른 브로커 주소를 통해 조회해도 같은 토픽 상태가 보이는가
- 브로커 재시작 후에도 동일하게 동작하는가

애플리케이션 기동 성공만으로 운영 준비가 완료됐다고 판단하지 않습니다. 클러스터 상태와 실제 메시지 왕복을 확인한 뒤 트래픽을 전달해야 합니다.

## 4. 트래픽 증가는 디스크 문제로 이어졌습니다

처리량이 늘면서 CPU나 메모리보다 먼저 디스크 사용량이 빠르게 증가했습니다. 원인을 확인해보니 한 영역만의 문제가 아니었습니다.

- DB 로그가 계속 누적됐습니다.
- 처리 이력 테이블의 데이터가 빠르게 증가했습니다.
- 애플리케이션 로그가 트래픽에 비례해 생성됐습니다.
- Kafka 토픽의 메시지가 필요한 기간보다 오래 보관됐습니다.

디스크가 가득 차면 로그를 남기지 못하는 수준에서 끝나지 않습니다. 데이터베이스와 Kafka가 정상적으로 파일을 기록하지 못해 서비스 장애로 이어질 수 있습니다.

다만 디스크를 확보하기 위해 로그와 데이터를 무조건 줄일 수는 없습니다. 장애 분석, 감사, 재처리와 데이터 복구에 필요한 범위를 먼저 정해야 합니다.

## 5. DB 로그와 테이블 데이터는 보존 목적을 기준으로 정리했습니다

DB 관련 데이터는 성격을 나눠서 봤습니다.

### DB 로그

- 장애 복구에 필요한 로그인지 확인합니다.
- 운영 감사에 필요한 보관기간을 확인합니다.
- 로그 회전과 압축이 적용되는지 확인합니다.
- 오래된 파일이 실제로 삭제되는지 주기적으로 점검합니다.
- 보관 정책을 변경하기 전에 복구 절차에 미치는 영향을 확인합니다.

### 테이블 데이터

- 온라인 조회에 필요한 기간을 정합니다.
- 오래된 데이터는 삭제, 요약 또는 별도 저장소 이관 중 적합한 방식을 선택합니다.
- 대량 삭제가 서비스에 부하를 주지 않도록 작은 단위로 처리합니다.
- 삭제 조건에 사용되는 컬럼과 인덱스를 확인합니다.
- 보관 작업의 성공 건수와 실패 건수를 기록합니다.

단순히 오래된 데이터를 지우는 것이 아니라 어떤 데이터가 온라인 서비스에 필요하고, 어떤 데이터가 장애 분석과 통계 목적으로 필요한지 구분했습니다.

## 6. 애플리케이션 로그는 필요한 정보만 남겼습니다

트래픽이 많은 시스템에서 요청마다 상세 로그를 남기면 로그 자체가 큰 부하가 됩니다. 디스크 쓰기와 로그 파일 관리 비용도 증가합니다.

다음 기준으로 로그를 조정했습니다.

- 정상 처리 로그는 집계 형태로 남깁니다.
- 오류 로그에는 원인을 찾는 데 필요한 최소 식별 정보만 포함합니다.
- 동일한 오류가 반복될 때 모든 스택 트레이스를 계속 남기지 않도록 조정합니다.
- 로그 파일에는 크기와 날짜 기준 회전을 적용합니다.
- 회전된 파일은 압축하고 정해진 기간 후 삭제합니다.
- 디버그 로그가 운영환경에서 계속 활성화되지 않도록 확인합니다.
- 수신, 성공, 실패와 필터 제외 건수는 분 단위 지표로 확인합니다.

로그를 줄인 뒤에는 장애 분석에 필요한 정보가 사라지지 않았는지 함께 확인했습니다. 로그량 감소 자체가 목적이 아니라, 같은 문제를 더 적은 로그로 찾을 수 있게 만드는 것이 목적이었습니다.

## 7. Kafka 보관주기는 서비스별 목적에 맞게 설정했습니다

모든 토픽에 같은 보관기간을 적용하면 불필요한 디스크 사용이 늘거나, 반대로 재처리에 필요한 메시지가 너무 빨리 사라질 수 있습니다.

토픽별로 다음 질문을 먼저 확인했습니다.

- Consumer 장애 시 최대 얼마 동안 재처리가 필요한가
- 메시지가 다른 저장소에도 안전하게 보관되는가
- 감사나 장애 분석에 원본 메시지가 필요한가
- 해당 토픽의 일평균 유입량과 메시지 크기는 어느 정도인가
- 파티션 수와 replication factor를 고려한 실제 디스크 사용량은 얼마인가

그 결과 서비스의 목적에 따라 `retention.ms`와 `retention.bytes`를 각각 설정했습니다. 시간 기준만 보지 않고 크기 제한도 함께 검토했습니다. `retention.bytes`는 파티션 단위로 적용되므로 전체 사용량을 계산할 때 파티션 수와 replica 수를 함께 고려해야 합니다.

상태의 최신값만 중요하고 key 단위로 이전 값을 정리할 수 있는 토픽은 `cleanup.policy=compact` 적용 가능성도 별도로 검토했습니다. 이벤트 이력이 필요한 토픽에는 무조건 적용하지 않았습니다.

보관기간을 줄인 뒤에는 가장 느린 Consumer도 메시지가 삭제되기 전에 정상적으로 처리할 수 있는지 확인해야 합니다. 보관주기는 단순한 디스크 절약 설정이 아니라 장애 복구 가능 시간과 연결된 운영 정책입니다. Kafka의 토픽별 보관 설정은 공식 문서의 [`retention.ms`, `retention.bytes`](https://kafka.apache.org/43/configuration/topic-configs/) 설명을 기준으로 확인했습니다.

## 8. 외부 시스템 연동에서는 보내야 할 데이터부터 줄였습니다

내부 처리 외에도 외부 시스템과 메시지를 주고받는 구간이 있었습니다. 내부 시스템보다 처리 성능이 낮은 외부 시스템에 모든 데이터를 그대로 전달하면 외부 구간의 지연이 전체 흐름으로 전파될 수 있습니다.

처음에는 전송 스레드나 배치 크기를 조정하는 방법을 생각했습니다. 하지만 처리할 필요가 없는 데이터까지 빠르게 보내는 것은 근본적인 해결이 아니었습니다. 먼저 외부 시스템이 실제로 필요로 하는 데이터 계약을 확인했습니다.

외부 전송 전에 다음 조건을 적용할 수 있는지 검토했습니다.

- 필수값이 없는 데이터 제외
- 외부 시스템이 지원하지 않는 유형 제외
- 계약된 대상만 통과시키는 allowlist 적용
- 동일한 데이터의 불필요한 반복 전송 방지
- 최신 상태만 필요한 경우 변경된 데이터만 전송
- 한 요청에 묶을 수 있는 데이터는 안전한 범위에서 배치 처리
- 전송 데이터 크기를 줄일 수 있는 필드 정리와 압축

필터링은 단순히 데이터를 버리는 작업이 아닙니다. 외부 시스템과 합의한 계약을 기준으로 해야 하며, 제외된 데이터의 건수도 확인할 수 있어야 합니다.

```text
내부 수신 건수
  → 유효성 검증
  → 외부 전송 대상 필터
  → 전송 시도
  → 성공 / 실패
```

수신 건수, 필터 제외 건수, 전송 성공과 실패 건수를 같은 시간 구간으로 비교하면 어느 단계에서 데이터가 줄거나 지연되는지 확인할 수 있습니다. 필터 조건을 변경할 때도 전후 건수를 비교해 의도하지 않은 데이터 누락이 없는지 검증해야 합니다.

외부 시스템이 느릴 때는 필터링뿐 아니라 다음 정책도 필요합니다.

- 요청 제한과 timeout
- 재시도 횟수와 간격
- 실패 데이터의 별도 보관
- 일시적인 장애가 내부 처리까지 확산되지 않도록 하는 차단 정책
- 외부 시스템이 회복된 뒤의 재처리 방법

필터링으로 전송량을 줄이고, 실패 격리와 재처리 정책을 함께 적용해야 전체 처리 성능을 안정적으로 유지할 수 있습니다.

## 9. 운영 반영 전후에 같은 지표를 확인했습니다

설정 변경 효과를 확인하기 위해 반영 전후에 같은 지표를 비교했습니다.

| 영역 | 확인 항목 |
|---|---|
| Kafka 클러스터 | broker 상태, controller, leader, replica, ISR |
| 토픽 | 파티션 수, 보관기간, 크기 제한, 디스크 사용량 |
| Producer | 전송 성공·실패 건수, 재시도, 전송 지연 |
| Consumer | 수신 건수, 처리 건수, lag |
| 데이터베이스 | 로그 증가량, 주요 테이블 증가량, 정리 작업 시간 |
| 애플리케이션 | 로그 증가량, 오류 건수, 디스크 사용률 |
| 외부 연동 | 필터 제외, 전송 성공·실패, 응답시간 |

운영 반영 순서도 중요했습니다.

1. 클러스터와 토픽 설정을 먼저 검증합니다.
2. 디스크 여유 공간과 증가 추세를 확인합니다.
3. 낮은 트래픽으로 메시지 왕복을 확인합니다.
4. 단계적으로 트래픽을 늘립니다.
5. 오류율과 지연이 기준을 넘으면 즉시 중단할 수 있도록 합니다.
6. 변경 전 설정으로 돌아갈 절차를 준비합니다.

한 번에 모든 설정을 바꾸면 어떤 변경이 효과를 냈는지 알기 어렵습니다. 클러스터, 토픽, 로그, 외부 연동 정책을 구분해 적용하고 각 단계의 지표를 확인하는 방식이 안전했습니다.

## 마무리

처음에는 Kafka 전송 오류를 애플리케이션 성능 문제라고 생각했습니다. 실제 원인은 클러스터가 의도한 상태로 구성되지 않은 상황에서 자동 토픽 생성이 활성화되어 있었고, 비정상 브로커에 만들어진 토픽을 정상적으로 사용할 수 없었던 것이었습니다.

이 문제를 확인한 뒤 운영환경에서는 자동 생성에 의존하지 않고 토픽과 설정을 배포 전에 명시적으로 관리해야 한다는 기준을 세웠습니다. 브로커 프로세스가 실행 중인지뿐 아니라 모든 브로커가 같은 클러스터에 참여하고 있는지, 토픽의 leader와 replica가 정상인지, 실제 메시지가 왕복하는지까지 확인해야 했습니다.

트래픽 증가에 따른 디스크 문제도 함께 다뤘습니다. DB 로그, 테이블 데이터, 애플리케이션 로그와 Kafka 메시지의 보관 목적을 구분하고, 서비스에 문제가 생기지 않는 범위에서 각각의 보관 정책을 조정했습니다.

외부 시스템 연동에서는 무조건 더 많이 보내는 것보다 필요한 데이터만 정확하게 보내는 것이 중요했습니다. 계약에 따른 필터링과 중복 방지로 전송량을 줄이고, 실패 격리와 재처리 정책을 함께 준비해야 처리량과 안정성을 모두 지킬 수 있었습니다.

운영 안정화는 설정 하나를 바꾸는 작업이 아니었습니다. 클러스터 구성, 토픽 관리, 디스크 보존 정책과 외부 시스템의 처리 한계를 하나의 흐름으로 보고 검증하는 과정이었습니다.
