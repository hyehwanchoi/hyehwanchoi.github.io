오래된 코드를 리팩터링할 때 가장 어려운 점은 코드를 새롭게 작성하는 일이 아니었습니다. 문서화되지 않은 기존 동작을 빠뜨리지 않고 유지하는 일이 더 어려웠습니다. 눈에 보이는 클래스만 읽어서는 실제 동작을 모두 설명할 수 없었고, 설정 파일과 공통 모듈, 데이터베이스 쿼리에도 중요한 조건이 흩어져 있었습니다.

이번 작업에서는 Codex와 Kiro를 함께 사용해 코드 탐색 범위를 넓히고, 변경 후보를 찾고, 회귀 테스트를 작성했습니다. 두 도구가 같은 결론을 냈다는 이유만으로 바로 반영하지는 않았습니다. AI의 결과는 답이라기보다 다음에 확인할 항목을 만드는 데 사용했습니다.

## 코드보다 먼저 동작을 목록화했습니다

처음에는 기존 코드와 새 코드를 바로 비교하려고 했습니다. 그러나 파일 단위 비교만으로는 호출 관계 뒤에 숨은 조건을 찾기 어려웠습니다. 그래서 먼저 기존 동작을 입력, 실행 조건, 결과, 예외 처리로 나눠 목록화했습니다.

```text
입력
  → 진입점
  → 조건 분기
  → 공통 처리
  → 외부 의존성 호출
  → 결과 저장
```

Codex와 Kiro에는 다음 질문을 반복해서 전달했습니다.

- 진입점에서 최종 결과까지 어떤 메서드가 호출되는가?
- 구현 클래스 밖에 있는 부모 클래스와 공통 모듈도 확인했는가?
- 정상 흐름과 반대 조건은 각각 어떻게 동작하는가?
- 값이 없을 때 아무 작업도 하지 않는 경우가 있는가?
- 변경이 다른 입력 유형에도 영향을 주는가?
- 코드만으로 판단할 수 없는 영역은 무엇인가?

이렇게 질문하자 단순한 코드 차이보다 확인하지 않은 영역이 먼저 보이기 시작했습니다.

## 오류를 막는 것과 기존 동작을 유지하는 것은 달랐습니다

AI는 예외가 발생할 수 있는 코드를 발견하면 기본값이나 방어 조건을 빠르게 제안했습니다. 일반적으로는 타당한 해결책이지만, 기존 시스템이 의도적으로 값을 설정하지 않던 경우에는 결과를 바꿀 수 있습니다.

예외가 사라졌다는 사실만으로 수정이 맞다고 판단할 수 없었습니다. 다음 내용을 함께 확인해야 했습니다.

- 기존 시스템에서도 같은 입력에 예외가 발생했는가?
- 값이 없는 상태 자체가 업무적으로 의미가 있는가?
- 기본값을 추가하면 이후 분기의 선택이 달라지는가?
- 한 경로만 수정해 다른 경로의 동작과 달라지지는 않는가?

AI가 제안한 방어 코드는 후보로 남겨두고, 기존 코드와 실행 결과를 확인한 뒤 반영 여부를 결정했습니다. 컴파일되는 코드와 기존 동작을 보존하는 코드는 서로 다른 문제였습니다.

## 리팩터링 기준을 테스트 가능성으로 잡았습니다

리팩터링의 목적을 클래스 수를 늘리거나 코드 길이를 줄이는 것으로 두지 않았습니다. 각 조건을 독립적으로 설명하고 검증할 수 있는지가 기준이었습니다.

- 어떤 입력에서 어떤 분기가 실행되는지 설명할 수 있는가?
- 공통 처리와 예외 처리를 구분할 수 있는가?
- 외부 시스템 없이 핵심 규칙을 테스트할 수 있는가?
- 한 단계의 결과가 다음 단계까지 유지되는지 확인할 수 있는가?
- 변경하지 않아야 할 기존 동작이 테스트로 고정되어 있는가?

Codex와 Kiro로 중복 코드와 공통화 후보를 찾았습니다. 이후에는 공통화가 오히려 개별 조건을 숨기지 않는지 다시 확인했습니다. 비슷해 보이는 코드라도 결과가 다르면 하나로 합치지 않았습니다.

## 테스트 개수보다 기대값의 근거가 중요했습니다

AI를 사용하면 테스트 코드 초안을 빠르게 만들 수 있습니다. 하지만 테스트가 많다는 사실만으로 변경이 안전해지는 것은 아닙니다. 잘못된 기대값을 가진 테스트는 잘못된 구현을 고정할 수도 있습니다.

테스트의 기대값은 다음 순서로 정했습니다.

```text
기존 코드 확인
  → 관련 설정과 쿼리 확인
  → 기존 실행 결과 확인
  → 기대값 확정
  → 테스트 작성
  → 변경 코드와 비교
```

정상 조건만 전달하면 AI가 정상 흐름 위주로 테스트를 만들기 쉬웠습니다. 그래서 반대 조건, 빈 값, 조회 결과 없음, 경계값과 여러 조건이 동시에 만족되는 경우를 별도로 요청했습니다.

테스트가 실패하면 곧바로 구현을 고치지 않았습니다. 구현 오류인지 테스트 기대값이 잘못된 것인지 먼저 구분했습니다. 이 과정에서 AI는 실패 원인의 후보를 정리하는 데 유용했지만, 최종 판단은 기존 동작의 근거를 다시 확인한 뒤 내렸습니다.

## 코드 밖의 조건도 확인해야 했습니다

애플리케이션 코드가 단순해 보여도 실제 조건이 설정이나 쿼리에 들어 있는 경우가 있었습니다. 메서드 이름만 보고 동작을 추측하면 중요한 조건을 놓칠 수 있었습니다.

다음 흐름을 하나의 검토 단위로 봤습니다.

```text
호출 조건
  → 실행되는 코드 경로
  → 외부 의존성의 조건
  → 변경되는 값
  → 유지되는 값
  → 최종 결과
```

Codex와 Kiro가 제시한 호출 경로가 다르면 실제 코드를 다시 확인했습니다. 두 도구 모두 언급하지 않은 영역도 별도로 검색했습니다. 분석 대상으로 제공하지 않은 파일은 AI가 확인할 수 없다는 점을 완료 조건에 반영했습니다.

기존 규칙을 발견했다고 해서 즉시 다른 계층으로 옮기지도 않았습니다. 규칙의 위치를 바꾸면 동시성이나 트랜잭션 경계, 성능 특성이 함께 달라질 수 있습니다. 테스트 기준이 충분하지 않은 상태에서는 발견과 제거를 별개의 작업으로 관리하는 편이 안전했습니다.

## 두 AI의 합의가 완료 조건은 아니었습니다

두 도구가 비슷한 답을 내놓으면 신뢰도가 높아진 것처럼 느껴질 수 있습니다. 그러나 같은 파일과 비슷한 질문을 제공하면 같은 범위만 보고 같은 부분을 놓칠 수도 있습니다.

AI 검토 뒤에도 개발자가 다시 확인해야 했던 항목은 다음과 같습니다.

- 진입점부터 최종 결과까지의 전체 호출 경로
- 부모 클래스와 공통 모듈의 숨은 분기
- 설정과 쿼리에 포함된 조건
- 값을 변경하는 동작과 변경하지 않는 동작
- 테스트 실행 결과와 기존 실행 결과
- 제공된 자료만으로 판단할 수 없는 영역

따라서 결과를 `동일`, `차이 있음`, `확인 불가`로 나눴습니다. 근거를 찾지 못한 항목을 동일하다고 처리하지 않았습니다.

## 누락을 줄이는 프롬프트

“빠진 로직이 없는지 확인해줘”라는 질문은 범위가 넓지만 완료 조건은 모호했습니다. 다음처럼 검토 과정과 산출물 형식을 함께 지정했을 때 결과가 더 유용했습니다.

```text
기존 동작을 기준으로 변경 후 결과가 같은지 검토해줘.
코드는 수정하지 말고 다음 순서로 분석해줘.

1. 진입점과 전체 호출 경로를 작성한다.
2. 부모 클래스, 공통 모듈, 설정과 쿼리를 확인한다.
3. 입력별 실행 조건, 결과, 예외 처리와 아무것도 하지 않는 동작을 표로 만든다.
4. 각 판단에 파일과 조건 단위의 근거를 붙인다.
5. 결과를 동일, 차이 있음, 확인 불가로 구분한다.
6. 확인할 수 없는 항목에는 추가로 필요한 자료를 적는다.
7. 앞선 분석이 틀렸다고 가정하고 반례를 다시 찾는다.

각 차이에 대한 재현 입력과 회귀 테스트 후보도 작성해줘.
```

프롬프트를 구체화해도 누락을 완전히 없앨 수는 없습니다. 대신 AI가 확인한 영역과 확인하지 못한 영역을 분리할 수 있습니다. 확정적인 답을 요구하기보다 미확인 영역과 반례를 드러내도록 요청하는 편이 더 현실적이었습니다.

## 마치며

Codex와 Kiro는 레거시 코드 탐색, 변경 후보 검토, 테스트 초안 작성과 실패 원인 분석에 유용했습니다. 같은 작업을 서로 다른 관점으로 검토하게 하면서 탐색 범위를 넓힐 수 있었습니다.

다만 AI의 결과는 완료 판정이 아니라 다음 검증 단계의 입력이었습니다. 기존 동작의 의미를 정하고 테스트 기대값을 확정하는 일은 코드와 실행 결과를 확인한 개발자가 수행해야 했습니다.

AI가 개발자를 대신한 것은 아니었습니다. 대신 개발자가 더 넓은 범위를 살펴보고, 더 많은 반례를 검토하고, 판단이 필요한 문제에 집중할 수 있도록 개발 과정을 바꾸어주었습니다.
