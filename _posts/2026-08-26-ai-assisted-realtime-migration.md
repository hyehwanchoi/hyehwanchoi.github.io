기존 시스템은 데이터를 10분 동안 모은 뒤 한꺼번에 처리했습니다. 처리 지연을 줄이기 위해 이 구조를 Kafka 메시지를 수신하는 즉시 처리하는 실시간 방식으로 전환하고, 데이터 흐름과 각 컴포넌트의 책임을 다시 정리하는 리팩터링을 진행했습니다.

가장 중요한 조건은 처리 방식과 코드 구조가 달라지더라도 기존 비즈니스 로직과 처리 결과는 바뀌지 않아야 한다는 것이었습니다. 하지만 업무 규칙이 구현 클래스뿐 아니라 추상 서비스, 메시지 생성 Helper, Mapper와 SQL에 분산되어 있어 변경 전후의 동작을 빠짐없이 비교하기가 쉽지 않았습니다.

이 과정에서 Codex와 Kiro를 활용해 구·신 시스템의 코드와 SQL을 비교하고, 데이터와 메시지가 만들어지는 전체 경로를 추적했습니다. 리팩터링 과정에서 기존 분기나 예외 처리가 누락되지 않았는지 검토하고 테스트로 확인했으며, 성능과 운영 안정성을 점검하는 과정에도 AI를 활용했습니다.

## 주기 처리에서 실시간 처리로

기존 시스템은 데이터를 일정 시간 동안 모은 뒤 조회하고 가공해 다음 시스템으로 전달했습니다. 각 처리 로직이 충분히 빨라도 실행 주기만큼의 대기는 피할 수 없었습니다. 데이터가 DB에 기록된 뒤 다시 조회되는 과정도 있었기 때문에 실제 지연이 어느 구간에서 발생하는지 파악하기도 쉽지 않았습니다.

신규 구조에서는 Kafka 메시지를 수신하면 바로 처리하고 다음 토픽으로 전달하도록 변경했습니다.

```text
수집 서비스
  → Kafka
  → 실시간 데이터 처리 서비스
  → Kafka
  → 후속 처리 서비스
```

하지만 Kafka Consumer를 추가하는 것만으로 전환이 끝나는 것은 아니었습니다. 신규 시스템이 빨라져도 기존과 다른 결과를 만든다면 사용할 수 없었습니다. 다음 조건을 함께 지켜야 했습니다.

- 기존과 동일하거나 대응되는 입력은 동일한 업무 결과를 만들어야 했습니다.
- 메시지의 필수 필드와 후속 시스템과의 계약을 유지해야 했습니다.
- 특정 유형에만 존재하는 예외 처리를 보존해야 했습니다.
- 실시간 구조 전환과 기존 업무 규칙 변경을 한 번에 진행하지 않아야 했습니다.

여기서 가장 먼저 필요했던 것은 코드를 고치는 일이 아니라 변경 범위를 알아내는 일이었습니다.

## AI로 코드가 아니라 확인 범위를 먼저 만들었습니다

한 메시지는 수신 클래스에서 시작해 파싱, 필터링, 마스터 데이터 조회, tracker별 버퍼, 메시지 생성과 Kafka publish 단계를 거쳤습니다. 눈에 띄는 구현 클래스 몇 개만 비교해서는 전체 동작을 설명할 수 없었습니다.

Codex와 Kiro에 기존 시스템과 신규 시스템의 관련 코드, Mapper, SQL, 설정과 실제 오류 메시지를 제공했습니다. 그리고 다음과 같은 질문을 반복했습니다.

- 이 필드는 처음 어디에서 만들어지고 최종적으로 어디에서 설정되는가?
- 구현 클래스 외에 부모 클래스나 Helper가 값을 변경하는가?
- 특정 유형에서는 이 값을 설정하지 않는 기존 분기가 있는가?
- Java가 아니라 SQL에서 결정되는 결과는 없는가?
- 이 수정이 다른 메시지 유형에도 영향을 주는가?
- NULL 방어를 추가하면 기존 결과가 달라지지 않는가?
- 구 시스템에는 있지만 신규 시스템에는 없는 처리가 더 있는가?

AI를 통해 데이터 흐름과 차이 후보를 빠르게 펼쳐놓을 수 있었습니다.

```text
Kafka 수신
  → 데이터 파싱
  → 유형별 필터
  → 마스터 데이터 조회
  → tracker별 버퍼
  → 최종 메시지 생성
  → Kafka publish
```

Codex에서 나온 분석과 Kiro에서 확인한 내용을 비교했습니다. 한쪽에서 새로운 후보가 발견되면 다른 쪽에서도 해당 조건의 영향 범위와 반례를 다시 검토했습니다. 두 결과가 다른 지점은 개발자가 먼저 확인해야 할 우선순위가 되었습니다.

이 방식은 모든 코드를 처음부터 순서대로 읽는 것보다 탐색 속도를 높여주었습니다. 개발자는 AI가 정리한 후보 중 실제 업무 결과에 영향을 주는 부분을 코드와 SQL에서 확인하는 데 집중할 수 있었습니다.

## 예외를 막는 것과 기존 동작을 유지하는 것은 달랐습니다

신규 시스템에서 특수 유형의 좌표값이 NULL이어서 오류가 발생한 적이 있습니다. 일반적인 해결 방법은 NULL일 때 기본 좌표를 넣는 것입니다. AI도 우선 방어 코드를 제안했습니다.

하지만 구 시스템을 다시 확인해보니 해당 유형에서는 원래 좌표를 설정하지 않고 다른 처리 경로로 이동하고 있었습니다. 기본값을 추가하면 오류는 사라질 수 있지만 기존 동작과는 달라집니다. 필요한 것은 NULL 방어가 아니라 구 시스템과 같은 분기였습니다.

상태값 누락도 비슷했습니다. 최종 메시지에 상태값을 넣는 코드만 추가해서 끝낼 수 없었습니다. 상태값이 어디에서 시작되고, 중간 객체에서 유지되며, 메시지 Builder와 공통 서비스까지 전달되는지 확인해야 했습니다. 하나의 구현 클래스에만 수정하면 다른 경로에서는 계속 빠질 수 있었습니다.

이때 Codex와 Kiro는 수정 위치 후보와 영향을 받는 경로를 찾는 데 사용했습니다. 실제 반영 여부는 구 시스템의 실행 결과와 전체 호출 경로를 확인한 뒤 결정했습니다.

AI가 오류를 막는 코드를 빠르게 제안하더라도 그 코드가 기존 업무 규칙을 유지한다는 보장은 없었습니다. 컴파일되는 코드와 맞는 코드는 서로 다른 문제였습니다.

## 리팩터링의 기준을 테스트 가능성으로 잡았습니다

실시간 구조로 전환하면서 데이터 수신, 버퍼 적재, 메시지 생성과 publish 책임을 구분했습니다. 메시지 생성 규칙과 마스터 데이터 조회 경계도 정리했습니다. 목적은 클래스를 더 많이 만들거나 코드를 짧게 만드는 것이 아니었습니다.

리팩터링의 기준은 다음과 같았습니다.

- 메시지가 어느 단계에서 만들어지고 변경되는지 설명할 수 있는가?
- 공통 처리와 유형별 예외 처리를 구분할 수 있는가?
- 반복적인 마스터 데이터 조회를 줄일 수 있는가?
- tracker별 데이터가 언제 버퍼에 들어가고 전송되는지 확인할 수 있는가?
- 각 처리 단계의 결과를 테스트할 수 있는가?

Codex와 Kiro로 중복 코드와 공통 처리 후보를 찾고, 메서드와 Helper의 책임을 검토했습니다. 리팩터링 후에는 다시 구 시스템과 신규 시스템을 비교해 기존 분기가 빠지지 않았는지 확인했습니다.

이 과정에서도 AI가 제안한 구조를 그대로 적용하지 않았습니다. 공통화하면 안 되는 유형별 처리까지 합쳐지지 않는지, 추상화 뒤에 업무 조건이 숨지 않는지를 다시 확인했습니다.

## 테스트 코드를 만드는 것보다 무엇을 검증할지 정하는 일이 먼저였습니다

AI에 대상 클래스를 제공하면 테스트 코드 초안을 빠르게 만들 수 있었습니다. 그러나 테스트 메서드가 많다는 사실만으로 리팩터링의 안전성이 보장되지는 않았습니다. 먼저 기존 시스템에서 유지해야 할 동작을 정리했습니다.

Java 처리에서는 다음 내용을 검증했습니다.

- 입력 유형에 따라 어떤 분기가 실행되는가?
- 상태값과 메시지 필드가 최종 publish까지 유지되는가?
- 좌표를 설정해야 하는 경우와 설정하지 않아야 하는 경우가 구분되는가?
- NULL과 특수 데이터가 기존과 동일하게 처리되는가?
- tracker별 버퍼가 건수 또는 시간 조건에 따라 전송되는가?
- 최종 Kafka 메시지가 기존 계약을 만족하는가?

테스트 클래스는 지나치게 세분화하지 않았습니다. 실제 처리 클래스에 대응하는 테스트 클래스 안에서 업무 시나리오별 테스트 메서드로 나눴습니다. 내부 메서드 호출 횟수보다 최종 결과를 중심으로 검증하려고 했습니다.

Codex와 Kiro는 테스트 후보와 경계 조건을 넓히는 데 활용했습니다. 정상 조건을 주면 반대 조건, NULL, 빈 조회 결과와 특수 상태 조합을 추가로 검토하게 했습니다. 생성된 테스트 코드는 실제로 실행했고, 실패 결과를 다시 AI에 제공해 구현 오류인지 테스트 기대값의 오류인지 분석했습니다.

중요한 점은 expected result를 AI가 정하지 않았다는 것입니다. 테스트의 기대값은 구 시스템의 코드, SQL과 실제 실행 결과를 기준으로 확정했습니다.

```text
코드 분석
  → 수정안 작성
  → 테스트 실행
  → 실패 결과 수집
  → AI 재분석
  → 기존 코드·SQL 확인
  → 수정 또는 제안 폐기
```

AI 활용은 한 번의 질문과 답변으로 끝나지 않았습니다. 구현과 테스트 결과를 다시 입력하면서 검증 범위를 반복적으로 좁혀갔습니다.

## SQL에 들어 있던 비즈니스 로직

Java 코드만 확인해서는 기존 동작을 설명할 수 없는 경우가 있었습니다. Mapper를 호출하는 Java 코드는 단순했지만 실제 판단은 동적 SQL과 UPDATE 조건 안에 들어 있었습니다.

쿼리 문자열이 기존과 같은지를 비교하는 대신 다음 흐름을 테스트 대상으로 삼았습니다.

```text
입력 조건
  → 실행되는 Mapper와 SQL 분기
  → 변경되는 행과 컬럼
  → 유지되는 기존값
  → 최종 메시지 결과
```

Codex와 Kiro를 사용해 SQL의 실행 조건, 변경 컬럼, 유지 컬럼과 테스트되지 않은 조합을 정리했습니다. 한쪽에서 발견한 조건이 다른 쪽에 없으면 실제 Mapper와 SQL을 다시 확인했습니다. 두 도구에서 모두 언급되지 않은 조건도 개발자가 SQL을 확인하면서 추가로 발견했습니다.

SQL에 비즈니스 규칙이 있다는 사실을 확인했지만 이번 전환에서 이를 Java로 옮기지는 않았습니다. 기존에 인수받은 구조였고, 테스트 기준이 충분하지 않은 상태에서 핵심 규칙을 옮기면 기존 결과가 달라질 위험이 컸습니다.

SQL의 원자적 UPDATE를 조회 후 Java에서 판단하는 방식으로 바꾸면 동시성 동작이 달라질 수 있습니다. 집합 기반 처리가 여러 번의 조회와 갱신으로 바뀌면 성능도 악화될 수 있습니다. 무엇보다 실시간 구조 전환과 업무 규칙 이동을 동시에 진행하면 장애가 발생했을 때 원인을 구분하기 어려워집니다.

이번 작업에서는 SQL 실행 조건과 데이터 변경 결과를 테스트로 확인하되 기존 SQL 규칙은 유지했습니다. 문제를 발견한 시점과 안전하게 제거할 수 있는 시점은 같지 않다고 판단했습니다.

## 실시간 전환이 성능 개선인지 Kafka 지표로 확인했습니다

주기 처리를 제거했다는 사실만으로 성능 개선이 완료됐다고 판단하지 않았습니다. Kafka Consumer Lag과 입력·출력 처리량을 확인했습니다. 측정 구간에서 유입량에 따라 Lag이 지속적으로 증가하지 않는지 살펴봤습니다.

다음 항목을 함께 확인했습니다.

- Kafka Consumer Lag
- 입력 메시지 처리량과 출력 메시지 처리량
- Kafka record timestamp와 애플리케이션 수신 시각
- Kafka publish 성공 시각
- tracker별 버퍼 체류시간과 flush 사유
- 후속 서비스로 전송되는 메시지 건수

성능 설정의 이름을 나열하기보다 어떤 가설을 확인하기 위해 설정과 지표를 봤는지가 중요했습니다. Consumer 수를 늘려도 할당 가능한 partition 수가 부족하면 실제 병렬성은 증가하지 않습니다. 버퍼 크기를 늘리면 전송 횟수는 줄어들 수 있지만, 저빈도 tracker의 대기시간과 메모리 사용량은 증가할 수 있습니다. 후속 서비스의 처리량이 충분하지 않다면 앞단만 빠르게 만드는 것으로 전체 처리량이 개선되지 않습니다.

Codex와 Kiro에 Producer·Consumer 설정, partition 구성, Verticle 인스턴스 수, 오류 로그와 Kafka Lag을 제공했습니다. AI를 통해 가능한 병목을 애플리케이션 메모리, Producer 내부 대기, broker metadata, Consumer assignment, 버퍼 체류와 후속 서비스 처리량으로 분리했습니다. 각 후보를 어떤 로그와 지표로 반증할지도 함께 정리했습니다.

## 메모리를 늘렸지만 오류는 계속됐습니다

Kafka에서 record batch가 만료되는 오류가 반복됐을 때 처음에는 애플리케이션 메모리를 의심했습니다. 메모리를 2GB에서 4GB로 늘렸지만 동일한 오류가 계속 발생했습니다.

메모리 증설이 효과가 없다는 결과를 확인한 뒤 조사 범위를 바꿨습니다. topic metadata, partition leader, Consumer assignment, Producer batch 체류시간과 Kafka Lag을 확인했습니다.

```text
batch expiration 발생
  → 메모리 부족 가설
  → 2GB에서 4GB로 증설
  → 동일 오류 지속
  → metadata·leader·assignment·전송 경로 확인
```

이 과정에서 AI는 오류 메시지별 원인 후보, 함께 확인해야 할 Kafka 상태와 로그 위치를 정리하는 데 사용했습니다. AI가 원인을 확정했다고 보지는 않았습니다. 실제 서버 상태와 Kafka 지표를 통해 맞지 않는 가설을 하나씩 제거했습니다.

## topic, partition, offset과 시간을 연결했습니다

동일한 AP MAC이 반복되거나 메시지가 늦게 도착한다는 주장이 나왔을 때 각 서비스의 로그만 따로 보면 서로 다른 결론을 내릴 수 있었습니다. 어느 구간부터 데이터가 반복됐는지 확인하기 위해 수집부터 후속 서비스 전송까지 공통 정보를 남겼습니다.

```text
수집 서비스 Kafka 수신
  → 수집 서비스 Kafka 송신
  → 처리 서비스 Kafka 수신
  → 필터링·버퍼 적재
  → 후속 서비스 Kafka 송신
```

로그에는 topic, partition, offset, tracker와 AP 식별자, Kafka record timestamp, 애플리케이션 수신 시각과 송신 시각을 연결했습니다. 버퍼 크기와 flush 사유, publish 결과도 함께 확인했습니다.

Codex와 Kiro에 각 클래스의 코드를 제공하고 수신 직후, 필터링 전후, 버퍼 적재와 최종 publish 성공 시점 중 어디에 로그를 넣어야 하는지 검토했습니다. 로그가 너무 많아지지 않도록 특정 tracker만 추적하거나 최종 메시지의 AP 종류와 중복 수만 남기는 방법도 함께 정리했습니다.

동일 AP MAC 반복 문제는 다음 순서로 확인했습니다.

```text
수집 서비스 출력 topic·partition·offset
  → 처리 서비스 입력 topic·partition·offset
  → AP ID
  → 마스터 데이터의 AP MAC
  → tracker별 버퍼
  → 최종 AP 배열
```

이를 통해 반복 데이터가 수집 서비스에서 이미 전달된 것인지, Kafka 메시지가 다시 처리된 것인지, 여러 AP ID가 같은 AP MAC으로 매핑된 것인지, 처리 서비스의 버퍼가 같은 AP 관측값을 여러 번 누적한 것인지 구분할 수 있었습니다. 로그로 확인되지 않은 원인은 단정하지 않았습니다.

## Codex와 Kiro를 적극 활용해도 누락은 남았습니다

두 도구를 사용하면서 한쪽에서 놓친 부분을 다른 쪽에서 발견하기도 했습니다. 코드 탐색과 테스트 작성 속도, 검토 범위는 분명히 넓어졌습니다.

하지만 두 도구의 결과가 비슷하다고 해서 누락이 없다고 판단할 수는 없었습니다. 분석 대상으로 제공하지 않은 파일은 확인할 수 없었고, 구현 클래스 뒤에 있는 추상 서비스나 SQL의 부정 조건이 빠지기도 했습니다. 값을 설정하지 않는 기존 동작을 일반적인 NULL 문제로 해석할 수도 있었습니다. 런타임 properties와 실제 Kafka 배포 구조는 소스 코드만으로 알 수 없었습니다.

AI 검토 이후에도 개발자가 다시 확인해야 했던 것은 다음과 같습니다.

- 구현 클래스뿐 아니라 추상 서비스와 Helper까지 포함한 호출 경로
- Java 코드 밖의 Mapper와 SQL 조건
- 값을 설정해야 하는 조건과 설정하지 않아야 하는 조건
- 실제 운영 properties와 Kafka partition 할당
- 테스트 실행 결과와 기존 시스템의 실행 결과
- 운영 데이터에서만 나타나는 특수 입력

두 AI의 합의는 완료 조건이 아니었습니다. AI 분석에 개발자의 코드 확인, SQL 결과, 테스트 실행과 운영 로그가 더해져야 변경 여부를 판단할 수 있었습니다.

그렇다고 개발자가 모든 코드를 처음부터 혼자 읽는 방식으로 돌아갈 필요는 없었습니다. AI로 탐색과 구현 속도를 높이고, 개발자는 업무 규칙의 의미와 변경 위험을 판단하는 데 집중하는 방식이 더 효과적이었습니다.

## 남은 과제: SQL 비즈니스 로직 분리

이번 전환에서 SQL 실행 조건과 데이터 변경 결과를 확인하고 테스트를 작성했지만, SQL에 포함된 비즈니스 규칙 자체는 유지했습니다. 이 부분은 명확한 기술 부채이자 다음 작업으로 남아 있습니다.

다음 단계에서도 Codex와 Kiro를 적극적으로 활용할 계획입니다.

먼저 두 도구를 이용해 Mapper와 SQL에서 호출 위치, 실행 조건, 변경되는 값, 유지되어야 하는 값, 트랜잭션과 부수 효과를 각각 목록화합니다. 두 결과를 실제 SQL과 비교해 개발자가 최종 규칙을 확정합니다.

그다음 아직 테스트되지 않은 조건을 보강하고, 기존 SQL 결과와 분리한 도메인 로직의 결과를 비교하는 테스트를 작성합니다. SQL의 집합 처리와 원자적 갱신은 DB에 남길지 검토하고, 상태 판단과 메시지 정책처럼 애플리케이션에서 관리해야 할 규칙을 구분해야 합니다.

이 작업은 아직 완료하지 않았습니다. 테스트가 확보된 규칙부터 단계적으로 진행하고, 동시성, 트랜잭션과 처리시간이 기존과 달라지지 않는지 검증해야 합니다.

## 마치며

이번 전환에서 Codex와 Kiro는 레거시 분석, 구·신 비교, 리팩터링 후보 탐색, 코드 수정안 작성, 테스트 생성, Kafka 성능 가설 정리와 진단 로그 설계까지 개발 과정 전반에 사용했습니다.

AI를 사용하면서 더 많은 코드를 더 짧은 시간에 검토할 수 있었고, 확인해야 할 조건과 가설도 넓어졌습니다. 테스트 실패와 운영 로그를 다시 입력해 수정안을 반복적으로 검증하는 과정도 개발 흐름의 일부가 되었습니다.

다만 AI의 결과는 완료 판정이 아니라 다음 검증 단계의 입력이었습니다. 기존 업무 규칙의 의미를 정하고, 테스트의 기대값을 확정하고, 운영 환경에서 변경을 적용할 수 있는지 판단하는 과정은 코드, SQL, 테스트와 실제 지표를 확인한 개발자가 수행해야 했습니다.

AI가 개발자를 대신한 것은 아니었습니다. 대신 개발자가 더 넓은 범위를 살펴보고, 더 많은 가설을 검토하고, 판단이 필요한 문제에 집중할 수 있도록 개발 과정을 바꾸어주었습니다.
